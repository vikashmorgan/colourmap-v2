What you built

One project, dim013-project, built step by step in class. It is graded on its history, and you submit the GitHub URL, not a zip.

  1. Skeleton · terminal only

    Folders data/ src/ tests/, README.md, requirements.txt, the sample CSV, and a hidden .env holding a placeholder key. No mouse.

  2. On GitHub

    Git set up, a repository, two commits (chore: then feat: with load_data.py), pushed to a public GitHub repository with a token.

  3. Branch & merge

    Two branches changing the same line: one fast-forward, one conflict resolved by hand into a merge commit. Then, in pairs, a pull request reviewed and merged.

  4. Layout

    The standard layout (data/raw, data/processed, notebooks/), a real README, and a .gitignore that keeps .env and .venv/ out.

  5. Reproducible

    A virtual environment, dependencies pinned in requirements.txt, and the proof: a fresh clone that installs and runs.

The oral defence

The teacher checks the definition of done, then you do the fresh clone live. For each point: what to show, and a sentence to say.

1 · A Conventional Commits history
Show git log --oneline.

Every commit is one logical change, named by its type: chore for setup, feat for a new function, fix for a bug, refactor for the same behaviour restructured, docs for documentation.

2 · The conflict's merge commit
Show git log --oneline --graph: the fork and the join.

Two branches changed the same line of load_data.py. The first merge was a fast-forward, because main had not moved. The second conflicted, so I kept both edits in one line, removed the markers, and committed: that merge commit has two parents.

3 · A merged pull request with a review
Show the PR on GitHub: the line comment, the answer, the merge.

My partner pushed a feature branch to my repository and opened a pull request. I reviewed a specific line, proposing an alternative with a reason; they answered, and I merged it, then pulled it into my main.

4 · The standard layout
Show the repository root on GitHub.

Raw data stays untouched in data/raw, cleaned data goes to data/processed, exploration in notebooks, code in src, tests in tests. Empty folders hold a .gitkeep, because Git tracks files, not folders.

5 · The README
Open README.md.

It says what the project does, how to install it, how to run it, and how to contribute: someone new can start from it alone.

6 · The .gitignore
Open .gitignore, run git status.

It keeps secrets (.env), the environment (.venv/) and clutter (__pycache__, .DS_Store) out of the repository. It does not remove a file already committed: that needs git rm --cached, and a leaked key must be changed.

7 · A requirements.txt that rebuilds on a fresh clone
Do it live: 
git clone <your-url> dim013-check
cd dim013-check
python -m venv .venv
source .venv/bin/activate      # Windows: .venv\Scripts\Activate.ps1
pip install -r requirements.txt
python -m src.load_data data/raw/sample.csv

A new folder and a new environment, nothing from my setup: if the first rows of the CSV print, the project is reproducible.

Key concepts

Why version control
Copies like final_v2.py, final_REAL.py record states, never changes or intent: you cannot tell what changed, who changed it, or safely go back. Git gives history, safety (return to any state) and collaboration. Its unit is the commit, a named snapshot.
The repository and .git
git init turns a folder into a repository by creating the hidden .git/, where all history lives. Delete .git/: the files stay, the history is gone.
The three areas (and the remote) 
working directory --add--> staging area --commit--> repository (.git) --push--> remote (GitHub)
The staging area is what you have chosen for the next commit: it lets one commit hold exactly one logical change. git status tells you which area each change is in.
Conventional Commits
<type>: <short description>, lowercase, imperative ("add", not "added"), no final period, about 50 characters.
TypeWhen
feata new capability
fixa bug corrected
docsdocumentation only
refactorrestructured, same behaviour
choretooling, config, dependencies
Branches and merging
A branch is a separate line of work starting from main. Merging brings it back:
  • Fast-forward: main had not moved, so Git just moves the label forward. No new commit.
  • Merge commit: both lines moved; Git joins them with a commit that has two parents.
  • Conflict: both changed the same line, so Git asks you. Edit the file, delete the <<<<<<< ======= >>>>>>> markers, git add, commit.
Remotes: push, pull, clone
origin is a nickname for the GitHub URL. push sends commits (not files: uncommitted work stays local), pull brings others' commits in, clone copies a whole repository. Your local repository has the full history, so you can work offline. GitHub wants a token, not your password.
Pull requests and code review (GitHub Flow)
Work on a feature/ branch, push it, open a pull request: a proposal to merge, with a summary, what changed, how to test. The reviewer comments on specific lines with a reason; the author answers with a new commit or a reply. Then it is merged.
Secrets and .gitignore
Secrets live in .env and must never reach GitHub. Until the .gitignore exists, add files by name. A token is a password: never in code, a commit or a chat.
Reproducibility: venv and requirements.txt
A virtual environment (.venv) holds this project's packages, apart from the rest of the computer. pip freeze > requirements.txt pins them, with exact versions. Every new package: install → freeze → commit. Anyone can then rebuild the same environment with pip install -r requirements.txt.

Key terms

Repository (repo)
A project folder whose history Git keeps, in .git/.
Commit
A named snapshot of the project, with author, date, message and a unique hash.
Hash
A commit's unique id, e.g. 7b21e04.
HEAD
Where you are now. HEAD~1 is one commit before.
Staging area (index)
The changes chosen for the next commit.
Untracked / tracked
A file Git does not follow yet / one it follows.
Branch
A movable label on a line of commits; main is the default.
Fast-forward
A merge that just moves the label, because nothing else happened.
Merge commit
A commit with two parents, joining two lines of work.
Conflict
Two branches changed the same line: you choose the result.
Remote / origin
A copy of the repository on a server; origin is its nickname.
Push / pull / clone
Send commits up / bring commits down / copy a whole repository.
Pull request (PR)
A proposal to merge a branch, discussed and reviewed on GitHub.
Personal access token
A password made for Git: limited permissions, expires.
.gitignore
Files Git should never track (secrets, environments, clutter).
.gitkeep
An empty placeholder so an empty folder reaches GitHub.
.env
A hidden file for secrets such as API keys. Never committed.
Virtual environment (venv)
A project's own set of Python packages.
requirements.txt
The pinned list of packages that rebuilds the environment.
Reproducible
Anyone can clone, install and run it, and get the same result.

Check yourself

Say the answer out loud, then open it.

What did git init create? What if you delete it?
The hidden .git/ folder with the whole history. Delete it: the files stay, the history is gone.
You ran git add README.md. Where is that change?
In the staging area: it goes into the next commit, not yet into the history.
Why were src/ and tests/ missing from the first commit?
Git tracks files, not folders: an empty folder does not exist for Git (hence .gitkeep).
Why add files by name in the first commits?
So .env, the secret, stays out before the .gitignore exists.
Fast-forward or merge commit: what decides?
Whether main moved since the branch started. Not moved: fast-forward. Moved: a merge commit with two parents.
Does git push send your saved files?
No: it sends commits. Changes not committed stay on your computer.
Your .env slipped into a commit. What now?
git rm --cached .env, add it to .gitignore, commit, and change (rotate) the key, because the old one is in the history.
The fresh clone fails with ModuleNotFoundError. Why?
A package is missing from requirements.txt. Fix the original: install, freeze, commit, push, clone again.
Which prefix? Renaming variables, output identical.
refactor. (Adding a --verbose flag: feat. .DS_Store in .gitignore: chore. A crash fixed: fix. A docstring: docs.)
